## 待复核（有推断成分，优先确认）

- [ ] `P1` **确认建行 `PM_Txn_Vrty_Cd=23` 就是积存金当日价**

  - 验收：交易日 10:30 之后跑 `npm run probe`，`建行日价` 的时间戳滚动到当日 10:30，且买入价向当日行情靠拢（此前点差 18~20 元的错位应塌回个位数）。

## 可靠性

- [ ] `P1` **服务端哨兵** —— 覆盖"本机断网无法自报"的盲区
  - 背景：取数与推送共用本机网络出口，断网时客户端无法通知你。已实测复现。
  - 方案：一台常驻小机器/云函数，交易时段内若收不到本机心跳（或京东报价时间戳停滞）就直接推 Bark。
  - 验收：拔掉本机网络 10 分钟内，手机收到"监控端失联"。
- [ ] `P2` **数据源多路兜底**：六家同源（都走京东），一旦该接口改签名，全部失效。至少接一路独立源（上金所基准或另一渠道）做交叉校验，并在偏差过大时提示。
- [ ] `P2` **接口失效的降级体验**：目前失效时托盘变 `×` 且推送一次；可再补"连续失败 N 次后降低轮询频率"，避免无效请求。
- [ ] `P3` **样本存储换 SQLite**：现在是单个 JSON 滚动 10 天，长期数据量上来后读写会变慢。

## 分发

- [ ] `P2` **代码签名与公证**（Apple Developer ID）：目前未签名，原生通知可能被系统丢弃，所以主通道走 Bark。若想恢复原生通知可靠性，需要签名 + 公证。

## 技术债

- 无自动化 UI 测试：界面改动只能靠人工验收，改动时要在 PR/对话里明确标注"需肉眼确认"。
- 两个数据源都是公开或逆向接口，字段随时可能变；每次发布前至少跑一次 `npm run probe`。
- `core/store.ts` 的"当日首笔"基准受程序启动时刻影响（午后启动会把午后价当成当日基准），与接口自带涨跌幅并存时优先用接口值。
- 面板渲染逻辑（`panel.js`）无类型检查，靠 `verify-vscode` 的同类逻辑间接覆盖。

## 开放问题（需要产品决策）

1. 是否只服务京东代销的六家？如果用户实际持仓在其他渠道（如工行App自有积存金），需要另开数据源。
2. Bark 用官方服务还是自建？自建可避免 device key 与推送内容经过第三方服务器。
3. 是否接受长期未签名分发（用户手动放行）？还是走 Developer ID 年费方案？
4. 浏览器插件优先 Chrome 还是 Safari/Edge？
